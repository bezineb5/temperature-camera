1 · Scope and responsibilities

This document defines protocol version 1 between a Raspberry Pi that reads a thermal sensor and a browser client that displays it. The client is index.html in this project; its decoder is the single entry point for sensor data, and the built-in demo encoder produces frames in exactly the layout described here.

Responsibility split
JobRuns onWhy
Read sensor, apply EEPROM calibration and bad-pixel correctionPiConstants are sensor-specific and belong nowhere else
Apply emissivity and reflected temperaturePiThe client should receive physically meaningful °C, not raw counts
Encode and send the framePiFixed 32-byte header, fixed payload
Decode the frameBrowserOne decoder, one format, no per-viewer server work
Palette, range, unit, overlays, smoothingBrowserThese are view state and change without a round trip
Recording, snapshots, downloadsBrowserOutput belongs with the viewer

2 · Transport

One WebSocket connection per viewer. Each thermal frame is one binary message; the client sets binaryType = 'arraybuffer' and hands each message straight to the decoder. Text messages are reserved for control and status (section 8) and never carry pixel data.

  • Message order is meaningful: sequence numbers increase by one per frame and wrap at 2³².
  • Frames are self-contained. There is no delta encoding, no keyframe, no dependency on the previous message.
  • When the socket is congested, drop the newest frame rather than queue it. A viewer that can only render 8 fps gains nothing from a backlog of 40 stale frames.
  • Compression is disabled on the socket. The payload is 1,568 bytes of near-incompressible integers; negotiation cost exceeds any saving.
  • Serving over plain ws:// is acceptable on a trusted LAN. Use wss:// whenever the page itself is served over TLS, or the browser blocks the connection as mixed content.

3 · Frame layout

Every message is a 32-byte header followed by columns × rows pixel values, all integers little-endian, no padding and no alignment gaps.

Payload

  • columns × rows values of int16, row-major, origin at the top-left pixel — the same orientation the client draws.
  • Each value is hundredths of a degree Celsius: 2143 is 21.43 °C. Resolution is 0.01 °C, finer than the sensor's own accuracy.
  • -32768 marks a pixel with no valid reading (see section 4).

Size

32 + 32 × 24 × 2 = 1,568 bytes per frame. At 12 fps that is 18.8 KB/s, about 150 kbit/s — roughly a tenth of a single MJPEG stream of the same scene at 640 × 480.

With flag bit 0 set, the payload becomes one float32 per pixel: 32 + 3,072 = 3,104 bytes. Use it for debugging or unusually wide ranges; hundredths cover every consumer case.

4 · Units, limits, missing readings

  • Every temperature on the wire is °C. Fahrenheit is a display option; it never reaches the socket.
  • Int16 hundredths span −327.67 °C to +327.67 °C, far wider than the sensor's −40 °C to +300 °C range.
  • A pixel that failed calibration, is masked as a bad pixel, or fell outside the sensor's valid range is sent as -32768. The client draws it as the bottom of the palette and excludes it from min, max and spot markers.
  • frameMinC and frameMaxC must be computed from valid pixels only. They are informational: the client's auto-range uses them as a starting hint but smooths its own scale, so a missing or stale value degrades the display rather than breaking it.
  • Values are integers on the wire by design. Do not send JSON arrays of decimals: 768 numbers as text cost four to six times the binary payload and force a parse per frame.

5 · What the stream must not carry

The palette and the temperature range are view state, not measurements. They stay in the browser, and the frame arrives as plain temperatures.

Excluded, and what breaks if it is included
Do not sendConsequence
A colorized RGB imageThe measurement is destroyed. Spot temperatures, min/max and re-analysis of a recording all become impossible.
The palette, or a "current palette" fieldChanging palette needs a Pi round trip and every viewer shares one look. Two monitors in one room cannot differ.
A normalized 0–255 fieldRange and palette are baked together. Manual range becomes impossible, and the normalization is lossy.
Upsampled pixels (any resolution above 32 × 24)Bandwidth multiplies for detail that does not exist. The client already interpolates when it scales to the canvas.
Overlays, reticles, timestamps, labelsPresentation belongs to the client, which knows the palette, the unit and the layout.

6 · Calibration stays on the Pi

Before a frame is encoded, the Pi is responsible for:

  • Reading the sensor's EEPROM calibration constants and applying them to raw counts.
  • Masking known bad pixels and interpolating or flagging them.
  • Applying emissivity (reported in the header so the client can display it) and reflected temperature.
  • Producing °C directly. The client performs no physical modelling and no unit conversion on the wire format.

A viewer that receives trustworthy °C can do its own display work. A viewer that receives raw counts would need a per-sensor constant table, which is exactly the coupling this contract exists to prevent.

7 · Faults, drops, reconnects

  • Sensor fault. Set flag bit 1 and still send a frame — the last good field, or a field of -32768. The client keeps rendering and marks the view as degraded. Do not stop sending; a silent socket is indistinguishable from a dead network.
  • Dropped frames. A sequence gap is the only signal the client needs. It must not panic, replay, or buffer: the next frame is complete on its own.
  • Reconnect. On reopen, the Pi starts a new sequence from whatever value it likes; the client only compares consecutive frames within one connection.
  • Slow client. Drop, never queue. The client discards any frame older than the one it just drew.
  • Idle socket. If no frame has arrived for two seconds, the client treats the view as stale and says so. A heartbeat on the control channel is optional but useful for distinguishing "no frames" from "dead socket".

8 · Control channel

Text messages, JSON, small and infrequent. Optional for v1 — a Pi may ignore all of them and still be conformant — but the client should degrade quietly when they go unanswered.

Palette, range, unit and overlay choices are deliberately absent: they never leave the browser.

9 · Recording and replay

Two artifacts, two purposes. The client produces the first today; the second is the reason to keep the raw frames.

.tframe logThe same 1,568-byte frames back to back, with no extra container. Replay is a loop feeding the decoder.Yes — palette and range are re-chosen at playback18.8 KB per second at 12 fps

A clip answers "what did the screen look like". A frame log answers "what were the temperatures" — the only form that survives a change of palette, a change of range, or a later question about a pixel. If long-term review matters, write both and keep them side by side.

10 · Versioning rules

  • version changes only for changes a v1 parser cannot survive: a different payload type, a reordered header, a different pixel meaning.
  • Appending fields is a v1-compatible change only if headerBytes grows and the payload starts at that offset. A v1 parser must honour headerBytes rather than assume 32.
  • Unknown flag bits are ignored, not rejected.
  • Unknown control message types are ignored without a reply.
  • The client rejects a frame whose declared dimensions do not match the grid it renders, and reports the mismatch rather than drawing scrambled data.

11 · Reference encoder

A complete Pi-side encoder. The struct is 32 bytes with no padding because the format string is little-endian and every field is naturally sized; nothing needs manual byte packing. 

import struct
import numpy as np

# version, flags, headerBytes, columns, rows, sequence,
# ambientC, frameMinC, frameMaxC, sensorMs, emissivity, reserved
HEADER = struct.Struct("<BBHHHIfffIHH")          # 32 bytes

def encode_frame(seq, sensor_ms, ambient_c, emissivity, temps_c):
    px = np.clip(np.rint(np.asarray(temps_c) * 100), -32767, 32767).astype("<i2")
    header = HEADER.pack(
        1,                                # version
        0,                                # flags
        HEADER.size,                      # headerBytes
        px.shape[1], px.shape[0],         # columns, rows
        seq & 0xFFFFFFFF,                 # sequence
        ambient_c,                        # ambientC
        float(px.min()) / 100,            # frameMinC
        float(px.max()) / 100,            # frameMaxC
        sensor_ms & 0xFFFFFFFF,           # sensorMs
        round(emissivity * 1000),         # emissivity
        0,                                # reserved
    )
    return header + px.tobytes()          # 1,568 bytes

# one binary message per frame
await websocket.send(encode_frame(seq, t_ms, 21.4, 0.95, temps_c))

The client mirrors this exactly: read the header, verify version, headerBytes and dimensions, read columns × rows values from headerBytes onward, divide by 100, and hand the resulting °C array to the renderer. In index.html that decoder sits between the frame source and the palette pipeline, so a live socket and the built-in demo are interchangeable.

12 · Assumptions and open questions

Assumptions behind v1

  • Sensor is an MLX90640 at 32 × 24. A 55 × 35 sensor (MLX90641) fits the header unchanged but raises the frame to 3,882 bytes.
  • Deployment is a trusted local network; the Pi serves the page and the socket.
  • Default stream rate is 12 fps. The sensor's own 1–64 Hz refresh is an implementation detail.
  • One viewer per socket is acceptable at this scale; there is no shared-frame fan-out.

Still open, and worth deciding before the Pi side is written:

  • Whether the Pi should also expose an MJPEG or RTSP output for an NVR or a non-browser consumer. If so, it is a second output fed from the same sensor read — not a replacement for this contract.
  • Whether a frame log is recorded on the Pi as well as in the browser, for retention beyond the session.
  • How a client states its preferred frame rate, if at all. At 1,568 bytes per frame it is hard to make a bandwidth argument for throttling, but a battery-powered laptop may still want it.
